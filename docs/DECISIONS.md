# Architecture Decisions


|| Bounded Gemini Candidate Evaluation (Checkpoint D6.2) | D6.1 bounded the downstream AI queue, but MatchEngine was calling Gemini for every job that passed deterministic filters BEFORE the enqueue budget was applied. D6.2 moves the Gemini boundary before NEW semantic evaluation: autonomous cycle runs deterministic-only filters first, selects top candidates (max_applications * 2), and only then invokes Gemini. Gemini budget = max_applications * 2. Application limit = max_applications. Deterministic rejects do not consume Gemini budget. Cached analyses do not consume NEW Gemini budget. Autonomous-cycle queue isolation (tracking enqueued_queue_item_ids) prevents pre-existing MANUAL/SCHEDULER items from bypassing the cycle budget. Gemini remains advisory; Python remains authoritative. D7 has NOT yet been validated. | 2026-10 |


|| Bounded Gemini Look-Ahead (Checkpoint D6.1) | Previously, `max_applications` was used as both the Gemini candidate cap AND the actual application limit. This prevented backup candidates when initial candidates were rejected (EXTERNAL or NEEDS_ATTENTION). Separated these concerns: `max_gemini_candidates = max_applications * 2` provides bounded look-ahead (backup candidates) while preventing uncontrolled Gemini usage. Actual application attempts remain capped at `max_applications`. Example: `max_applications=2` enqueues 4 candidates to Gemini, but only attempts 2 applications. If the first 2 candidates are rejected, the system can evaluate candidates 3 and 4. This enables multi-application runs without uncontrolled AI processing. All existing safety rules, quota handling, and current-run isolation preserved. | 2026-10 |


| Post-Click Reload Confirmation (Checkpoint D5) | Naukri instant-apply updates the job page server-side after submission. The Applied badge (`#already-applied`) only becomes visible after the page reloads — not within the initial 8-second in-page polling window. `start_application()` now performs one bounded reload (20s, `domcontentloaded`) after the in-page timeout and re-runs `detect_applied_state()`. A reload-confirmed Applied state is strong evidence because Naukri must have persisted the application server-side. This is NOT a retry of the Apply click. Reload failure returns `NEEDS_ATTENTION` safely. Single reload only — no loop. Confirmed live: Job 23 shows `#already-applied` span after reload. | 2026-10 |


| Pre-Analyzed Candidate Bypass (Checkpoint D4) | When `_apply_hard_filters_and_enqueue` finds jobs that already have AI analyses, count them as `pre_analyzed` (not `hard_filtered`). The early-exit check now requires both `queued == 0` AND `pre_analyzed == 0`. This allows the cycle to proceed to applications using valid existing analyses without re-burning Gemini quota. | 2026-10 |

| Title Scope Gate Canonicalization (Checkpoint D4) | The final safety gate's job-title scope check previously used strict substring matching against configured search titles (e.g. "Python Developer Fresher"), which incorrectly rejected real jobs titled "Python Developer". Replaced with `title_matches_allowed_role()` — the same deterministic function used by MatchEngine role targeting. This ensures consistent scope enforcement across filtering and safety gate boundaries. | 2026-10 |

| Discovery Failure Safety (Checkpoint D) | Live discovery failure must not fall back to historical DB jobs. The autonomous cycle now tracks the current DiscoveryRun and only processes jobs with `discovered_at >= current_run.started_at`. If `current_run.jobs_discovered == 0`, the cycle stops immediately with a discovery failure error. The adapter raises an exception instead of silently returning when homepage navigation fails, ensuring discovery failures are propagated. This prevents false appearance of fresh live search when no current cards were obtained. | 2026-10-06 |

| Autonomous Cycle Command (CHECKPOINT C) | Command-line interface for running the complete autonomous job application cycle with `--max-applications`, `--dry-run`, and `--max-jobs` flags. Calls existing services (DiscoveryService, MatchEngine, AIQueueService, ApplicationRunner) in sequence. Excludes S&P job `300926927428`, skips external jobs, re-classifies native/external before click, requires post-click Applied evidence, stops on AUTH/SECURITY/limits/errors. Outputs per-job decision table and summary. No input() prompts. Exit code 0 on normal completion, non-zero on stops. | 2026-10-02 |

| Header-Scoped Naukri Apply Control (Checkpoint B) | Naukri may expose duplicate `id="apply-button"` controls in the job header and sticky header. Resolve the visible `#job_header button#apply-button` first for both classification and click; only when no header match exists, use the first visible global `button#apply-button`, and log the selection. Header applied evidence takes precedence while post-click form/banner evidence remains supported. This prevents strict-mode ambiguity and never classifies or clicks generic apply controls. Offline only; external-first classification and all existing safety gates remain unchanged. | 2026-10-02 |

| Application-Type Settling and Ambiguity (Phase 10) | Preserve external-first and visible-native evidence, then perform one bounded 500 ms re-observation only when neither is visible. Return `AMBIGUOUS` when evidence remains absent; map it to `NEEDS_ATTENTION` before application creation so unknown never becomes native. Offline suite passed 96 adapter tests; live read-only validation made no application changes. | 2026-10-01 |
| Phase 10 Live Candidate Boundary | On 2026-10-01, use the existing authenticated persistent Playwright session for one bounded read-only discovery pass before any real application. Stop when no fresh candidate satisfies duplicate protection, native classification, and deterministic filters; do not broaden the search indefinitely or invoke Gemini/ApplicationRunner without an eligible candidate. This pass found no safe candidate, made no Apply/Submit action, and left automated successful applications at 0. | 2026-10-01 |
| Phase 10 Database Schema Migration | Additive ALTER TABLE with column existence checks; runs idempotent during startup before request handling; validates schema compatibility in /readiness endpoint; preserves all existing data; supports both SQLite and PostgreSQL with standard SQL; local SQLite database migrated and verified (10 records preserved, no data loss); Neon migration deferred to production deployment step. | 2026-10-01 |
| Evidence-Driven Native Application Boundary (Phase 10) | Native application success requires bounded post-click visible Applied evidence: `#already-applied`, `.already-applied`, exact visible "Applied", or `Applied to "<title>"` banner. A visible application container enters question handling; hidden, disabled, readonly, zero-sized, and hidden-type inputs are ignored. Native/external classification completes before creating APPLICATION_STARTED and repeats immediately before the click; mismatch aborts to external. Unresolved EXTERNAL_APPLICATION and NEEDS_ATTENTION attempts require manual reset. Implemented and tested offline only; no live submission occurred. | 2026-10-01 |
| Strict Question Detection Scoping (Phase 10) | Question detection scopes to visible application containers only. Each field must be: visible, enabled, non-zero box, not readonly, not disabled, not hidden-type, and not a header/search input. Rejects zero-sized elements. Associates labels via `for` attribute or placeholder. Implemented in `detect_application_questions()` with multiple rejection criteria. | 2026-10-01 |
| Experience Computation Consistency (Phase 10) | `compute_profile_experience_years()` replaces `len(experience)` everywhere: computes actual elapsed years from `start_date`/`end_date` fields, falls back to entry count if dates unparseable. Applied uniformly in safety gate and runner. The +2 year tolerance is preserved and reported. | 2026-10-01 |
| Bounded Post-Apply Wait (Phase 10) | After clicking Apply button, wait up to 8 seconds for explicit post-click evidence: Applied state OR visible application container. No inference from click, URL change, or HTTP 200. If neither evidence appears within timeout, return NEEDS_ATTENTION (no retry without manual reset). | 2026-10-01 |
| Post-Click Applied State Evidence (Phase 10) | Applied state requires visible evidence only: element with ID/class `already-applied`, exact text "Applied", or text starting with `Applied to "`. Inner text comparison; HTML-only matches rejected. Returns evidence text for persistence. | 2026-10-01 |

| Test Database Isolation | Backend tests must never reset the local runtime database. | Centralized Frontend API Client | Phase 8.4 routes every frontend API request through one Vite-configured client so hosted deployments cannot accidentally mix relative URLs, legacy variables, and localhost URLs. |
| Distributed Work Coordination | Phase 8.5B implements worker-owned AI queue work claiming without multi-processing dependencies. PostgreSQL uses atomic SELECT...FOR UPDATE SKIP LOCKED for true atomicity; SQLite uses transaction-safe fallback with deterministic ordering. Stale recovery preserves application safety: if max_attempts exceeded, escalates to NEEDS_ATTENTION rather than blindly retrying. Work ownership is strict: only claiming worker can heartbeat/release/complete/fail. Existing duplicate detection, safety gates, and application limits remain authoritative and unchanged. Future cloud browser execution deferred to Phase 8.5C+. |
| Coordination Service Separation | WorkCoordinationService is separate from AIQueueService (which handles Gemini processing). Coordination is purely about work ownership and availability, not application logic. This allows multiple workers to claim work without duplicating AI queue business logic. |
| PostgreSQL-Specific Locking | PostgreSQL claiming uses SELECT...FOR UPDATE SKIP LOCKED to prevent race conditions. SQLite compatibility is explicitly documented as transaction-safe fallback (without row-level locking). Database dialect detection enables conditional behavior without runtime failures. Tests cover both paths. |
| Safe Stale Recovery | Stale work recovery escalates to NEEDS_ATTENTION if max_attempts exceeded rather than automatically retrying. This preserves the safety principle: uncertain execution outcomes (browser crash, no heartbeat, exhausted attempts) require human review before reapplication. Existing duplicate detection and safety gates remain authoritative. |
| Heartbeat-Based Staleness | Stale detection uses last_heartbeat_at timestamp (30-minute threshold). Items without recent heartbeat from claiming worker are considered stale. Completed, failed, and needs_attention items are never marked stale. This prevents false positives for terminal work states. |
| Naukri Security Detection Uses Visible Text (Phase 9B-3) | `_check_security()` evaluates rendered `body` text instead of raw HTML so internal state such as `"showCaptcha":false` cannot create a false security block. Bare `captcha` is not sufficient by itself; explicit visible CAPTCHA widgets, human-verification phrases, security challenges, login indicators, and blocked-access indicators still stop automation. The change preserves the no-bypass safety boundary and requires another real visible-browser dry-run before live validation is complete. |
| Work Lifecycle Idempotence | Complete operation is idempotent: calling complete_work twice on same item returns success (already completed). Fail operation is terminal: each worker calls fail once. Release creates backoff (5-minute available_at) to prevent hammer-retry behavior. |
| Deterministic Work Ordering | Work claiming orders by priority descending, then created_at ascending. This ensures reproducible, consistent work assignment across runs and database backends. Prevents priority inversion or unpredictable ordering. |
| Ownership-Strict Operations | Heartbeat, release, complete, and fail operations require ownership (claimed_by == worker_id). Non-owning worker attempting operation raises WorkNotOwnedError. Prevents work theft and accidental overlap. Completed work is exempted from ownership checks (idempotent safety). |
| Duplicate ERROR Recovery | When a duplicate resume upload finds an existing profile in `ERROR` status, the service re-reads the stored PDF and re-runs the full extraction pipeline (PDF text + Gemini) against the existing profile record. No new resume or profile records are created. `CONFIRMED` and `REVIEW_REQUIRED` duplicates are reused without re-extraction. `confirmed` remains `false` until the user explicitly confirms. |
| prompt_version Versioning Constant | `AIQueueService.process_item()` now imports and uses `JOB_ANALYSIS_PROMPT_V1` from `prompts.py` instead of a hardcoded `"v1"` literal. Ensures `prompt_version` is always non-null, traceable to the actual prompt used, and updated in one place when prompts change. |
| Experience Year Computation | `MatchEngine.evaluate_job()` now uses `compute_profile_experience_years()` instead of `len(experience_list)`. Computes actual elapsed years from `start_date`/`end_date` fields in experience entries. Falls back to entry count when dates are unparseable. Correctly represents users with near-zero actual experience (e.g. future start dates). |
| Phase 9A Scheduler Orchestration Loop | Scheduler now orchestrates complete pipeline: discovery → hard filters → AI queue → ApplicationRunner. All three audit gaps fixed: (C1) AI queue auto-processes after discovery, (C2) ApplicationRunner invoked for completed AI jobs, (C3) hard filters integrated into runtime path. Hard filters remain authoritative (Gemini advisory only). ApplicationRunner remains sole executor. Final safety gate always runs. |
| Hard Filter Integration in Runtime Path | Hard filters (MatchEngine) evaluated on discovered jobs before AI queueing. Jobs failing hard filters are blocked from entering application path. Deterministic rules take priority; AI analysis provides advisory signal only. Guarantees deterministic behavior and prevents waste on unsuitable jobs. |
| Failure Isolation in Scheduler Cycle | Single job processing failures don't cascade. Try-catch in loop ensures next job processes safely. Quota exhaustion stops gracefully without applying. State machine preserved: discovered → filtered → queued → analyzed → applied. Missing profile/preferences skipped gracefully. Ensures robustness across diverse job datasets. |
| Scheduler Methods Separation | Three distinct orchestration methods: _apply_hard_filters_and_enqueue (filtering+queueing), _process_ai_queue_items (AI analysis), _invoke_application_runner (execution). Each returns stats. Main cycle calls sequentially. Clean separation enables future phase-specific tuning without cross-phase coupling. |
| No New Queue Created | Phase 9A reuses existing AIQueueService, AIQueueItem, and job/analysis models. No ApplicationQueueItem or new queue structures introduced. Keeps architecture simple and preserves all existing safety mechanisms (quota handling, retry logic, duplicate protection, stale recovery). |
| Scheduler API Endpoint | New /scheduler/run-cycle POST endpoint enables manual cycle execution for testing. Existing start/stop/pause/resume/status endpoints unchanged. Scheduler still runs automatically at configured interval. Manual execution and automatic execution both use same internal _run_discovery_task method. |
| Application Dry-Run Must Stop Before Native Apply (Phase 9B-4) | Because native Apply semantics remain UNKNOWN, `dry_run=True` is now a pre-Apply inspection boundary. It records `is_dry_run`, does not call `start_application()`, and cannot trigger remote application action. APPLIED/SUBMITTED remain the only duplicate-blocking statuses; click-only starts are not reported as FORM_OPENED. | 2026-10-01 |
| Checkpoint C2 fresher and IT gates | Use a configurable zero-year experience cap and deterministic IT metadata plus title keywords at both match and final safety gates. Missing metadata is unsafe and skipped. Native questions stop with `NEEDS_ATTENTION`; answering remains opt-in and defaults false. External links are recorded but never clicked. | 2026-10-06 |
